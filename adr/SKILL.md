# ADR: запись архитектурных решений

ADR (Architecture Decision Record) — иммутабельный документ, фиксирующий **одно** значимое решение: почему оно принято, что именно решено, какие правила оно вводит и чего стоит. ADR — журнал решений, а не описание текущего состояния системы: актуальное поведение описывают обычные документы в `docs/`, ADR отвечает на вопрос «почему так».

Файлы скилла:

| Файл | Назначение |
|---|---|
| `templates/adr.md` | Шаблон нового ADR |
| `templates/readme-index.md` | Шаблон индекса `docs/adr/README.md` |
| `templates/adr-0001-record-architecture-decisions.md` | ADR 0001 о принятии практики ADR (для bootstrap) |
| `templates/agents-rule.md` | Правило для файла инструкций агентов (для bootstrap) |

## Шаг 0: есть ли в проекте инфраструктура ADR

При каждом вызове скилла сначала проверь, ведутся ли в проекте ADR:

1. Поищи каталоги: `docs/adr`, `doc/adr`, `docs/decisions`, `docs/architecture/decisions`, `adr`, `decisions`, а также файлы по шаблону `**/[0-9][0-9][0-9][0-9]-*.md` в `docs/`.
2. Поищи упоминания ADR в `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, `.junie/guidelines.md`, `README.md`, `CONTRIBUTING.md` и в карте документации (`docs/README.md`, `docs/architecture.md`, `docs/index.md`).

Дальше:

- **ADR уже ведутся** (в любом каталоге и формате) — используй найденный каталог и его конвенции, не создавай параллельную структуру. Если не хватает отдельных частей (индекса, правила для агентов), доделай только их по шагам bootstrap ниже. Переходи к разделу «Процесс».
- **ADR нет** — выполни bootstrap, затем пиши ADR по запрошенному решению по разделу «Процесс».

## Bootstrap: разворачивание инфраструктуры ADR

1. **Язык.** Определи язык документации по `README.md`, `docs/` и файлу инструкций агентов. Если однозначно определить нельзя, спроси пользователя одним вопросом. Шаблоны скилла написаны на русском — при другом языке переведи заголовки разделов, статусы и подписи шапки, сохранив структуру.
2. **Каталог.** Создай `docs/adr/`. Если в проекте документация лежит в другом корне (`doc/`, `documentation/`), используй его: `<docs-root>/adr/`.
3. **ADR 0001.** Создай `docs/adr/0001-record-architecture-decisions.md` по `templates/adr-0001-record-architecture-decisions.md`: подставь дату, путь к каталогу и имя файла инструкций агентов. Он фиксирует саму практику и её правила, чтобы следующим участникам не нужно было знать о скилле.
4. **Индекс.** Создай `docs/adr/README.md` по `templates/readme-index.md` со строкой для ADR 0001 и пустой таблицей связей (оставь только заголовок таблицы).
5. **Правило для агентов.** Добавь правило из `templates/agents-rule.md` в файл инструкций агентов:
   - если есть `AGENTS.md`, добавь в раздел с общими правилами (или отдельным разделом в конец);
   - если вместо него используется `CLAUDE.md`, `.github/copilot-instructions.md` или аналог, добавь туда;
   - если файлов несколько, добавь в основной (тот, на который ссылаются остальные), а не дублируй;
   - если файла инструкций нет, создай `AGENTS.md` с заголовком и этим разделом и скажи об этом пользователю.
6. **Навигация.** Если в проекте есть карта документации (`docs/README.md`, `docs/architecture.md`, `docs/index.md`) или раздел «Документация» в корневом `README.md`, добавь туда ссылку на `docs/adr/README.md` с одной строкой описания. Новые карты документации не создавай.
7. **Первое решение.** Если скилл вызван ради конкретного решения, оформи его как ADR 0002 по разделу «Процесс». Если пользователь просил только наладить инфраструктуру, остановись после шага 6.

Не пиши ADR задним числом по прошлым решениям, если пользователь об этом не просил. Если просил — помечай такие ADR в шапке строкой `**Зафиксировано ретроспективно:** YYYY-MM-DD` (дата написания), а в `**Дата:**` ставь известную или приблизительную дату решения (`≈2025-03`); контекст и решение восстанавливай по коду, истории git и задачам, явно отмечая предположения.

В итоговом сообщении перечисли созданные и изменённые файлы.

## Когда ADR нужен

Пиши ADR, если изменение подходит хотя бы под один пункт:

- новая модель данных, таблица или поле с собственной семантикой; удаление таблицы или поля;
- изменение публичного API или контракта: эндпоинты, коды ошибок, формат ответа, сигнатура сообщений очереди, формат артефактов;
- новая интеграция, смена вендора, транспорта, SDK или модели (LLM, почта, хранилище);
- смена подхода: источник правды, синхронный → асинхронный процесс, env → БД, polling → webhook;
- новые инварианты транзакций, блокировок, идемпотентности, ретраев или порядка обработки;
- исправление инцидента, которое меняет поведение системы, а не просто возвращает задуманное;
- осознанный отказ от фичи или ограничения (удаляем окно времени, нормализацию и т.п.);
- изменение, которое нельзя выкатить обычным rolling update или нельзя откатить;
- решение владельца продукта, влияющее на архитектуру (ПДн, ретеншн, доступ).

ADR **не нужен** для чистого рефакторинга без изменения поведения, багфикса, возвращающего задуманное поведение, косметики, обновления зависимостей без смены API. Если сомневаешься — спроси пользователя одним вопросом, а не пропускай молча.

## Процесс

1. **Изучи конвенции репозитория.** Прочитай `docs/adr/README.md` и 3–5 последних ADR. Если стиль репозитория отличается от этого скилла (язык, формат шапки, названия разделов), следуй репозиторию: последние ADR важнее шаблона. Если в проекте есть карта документации (например, `docs/architecture.md`) или правила в `AGENTS.md`, учитывай их.
2. **Найди связанные ADR.** Поищи `grep` по ключевым сущностям (модели, поля, эндпоинты, акторы, вендоры) в `docs/adr/` и в таблице связей индекса. Определи тип связи с каждым (см. «Связи между ADR»).
3. **Выбери номер и slug.** Номер — максимальный существующий + 1, четыре цифры с ведущими нулями (`0067`). Slug — короткий kebab-case на английском, описывает решение, а не проблему: `no-retry-for-non-idempotent-posts`, `otp-request-log`. Файл — `docs/adr/NNNN-slug.md`. Перед созданием убедись, что номер не занят (в том числе в соседних ветках, если пользователь о них говорил).
4. **Собери факты из кода.** ADR пишется по фактической реализации или по согласованному плану. Каждое упомянутое имя (модель, поле, файл, env-переменная, актор, очередь, миграция, CronJob) проверь `grep`-ом. Не выдумывай номера миграций, имена и цифры; если чего-то ещё нет — так и напиши или спроси.
5. **Заполни шаблон** `templates/adr.md` по правилам разделов ниже. Необязательные разделы удаляй целиком, не оставляй пустыми.
6. **Обнови связанные ADR** — только шапку статуса и строку-указатель (см. «Иммутабельность»).
7. **Обнови индекс** `docs/adr/README.md` (см. «Индекс»).
8. **Обнови смежную документацию**, если решение меняет описанное в `docs/` (модель данных, API, потоки, runbook'и): документы описывают текущее поведение, ADR — причину.
9. **Пройди чек-лист** в конце этого файла.

## Структура ADR

Канонический порядок разделов. Обязательные отмечены ✱.

| Раздел | Назначение |
|---|---|
| Заголовок ✱ | `# ADR NNNN: <суть решения>` |
| Шапка ✱ | `**Статус:**`, `**Дата:**`, при наличии — `**Заменяет:**` / `**Частично заменяет:**` / `**Уточняет:**` |
| `## Контекст` ✱ | Проблема и почему её надо решать сейчас |
| `## Решение` ✱ | Что именно решено, с подразделами `###` по аспектам |
| `## Инварианты` ✱ | Таблица правил, которые должны соблюдаться после изменения |
| `## Последствия` ✱ | Цена, риски, влияние на пользователей и эксплуатацию |
| `## Рассмотренные и отклонённые альтернативы` | Таблица «Вариант / Почему отвергнут» |
| `## Развёртывание` | Порядок выкатки, если обычный rolling update не подходит |
| `## Реализация` | Ключевые файлы и модули с кратким описанием изменений |
| `## Ссылки` ✱ | Связанные ADR, файлы, планы, инциденты |
| `## Коррекция YYYY-MM-DD: …` | Только дописывается позже (см. «Коррекции») |

### Заголовок

- Формулируй **решение**, а не проблему: «Запрет ретраев неидемпотентных POST-запросов», а не «Проблема с повторным OTP».
- Идентификаторы — в обратных кавычках: «Журнал попыток входа по OTP (`otp_request_log`)».
- При замене подхода удобна форма «X вместо Y»: «Прямая SQS-интеграция с Recruitee вместо S2S-прокси».

### Шапка

```markdown
**Статус:** Принято
**Дата:** 2026-10-05
**Частично заменяет:** [ADR 0033](0033-slug.md), [ADR 0036](0036-slug.md)
**Уточняет:** [ADR 0053](0053-slug.md) (раздел «Плеер и деградация»)
```

- Статусы: `Предложено` (черновик до согласования и реализации), `Принято`, `Заменено [ADR NNNN](…)`, `Частично заменено [ADR NNNN](…)`, `Отклонено`.
- Дата — ISO `YYYY-MM-DD`, день принятия (обычно день мержа реализации).
- Строки связей — ссылками на файлы; для частичной связи в скобках укажи затронутый раздел или аспект.

### Контекст

- Опиши, что было до решения и почему это плохо. Факты, а не оценки: даты, идентификаторы заявок и объектов, Sentry issue, trace id, замеры, объёмы, таймлайн инцидента списком с временем.
- Перечисли ограничения: требования продукта, вендора, инфраструктуры, обратная совместимость.
- Не описывай здесь решение. Завершай формулировкой потребности: «Нужен журнал попыток входа, который хранится дольше логов и виден HR в админке».

### Решение

- Конкретно и проверяемо: имена моделей, полей, таблиц, индексов, эндпоинтов, env-переменных, акторов, очередей, CronJob'ов, номера миграций, значения по умолчанию, лимиты и таймауты с единицами.
- Разбивай на подразделы `###` по аспектам: модель, API, транзакционность, конкурентность, админка, очистка, фронтенд, наблюдаемость.
- Перечисления (поля, статусы, исходы, маппинги) — таблицами.
- Неочевидный выбор объясняй рядом с ним: «btree, а не GIN trgm, потому что…». Если у локального под-решения были варианты, дай небольшую таблицу вариантов прямо в подразделе и отметь выбранный жирным.
- Для алгоритмов — нумерованные шаги; для контрактов — точные значения (`detail` ровно `Step is not current`).
- Явно назови границы: что решение **не** гарантирует, какие пути не покрыты, что вынесено в отдельную задачу.
- Попутные изменения из того же релиза, не связанные с сутью, — в подраздел `### Попутно`.
- Решения владельца продукта помечай автором-ролью и датой: «Решение владельца продукта (2026-10-01)».

### Инварианты

Таблица `| Аспект | Правило |`. Это контракт для будущего кода: что нельзя нарушить, не написав новый ADR.

- Формулируй как правило, а не как описание: «POST без `Idempotency-Key` не повторяется автоматически».
- Каждое правило должно быть проверяемым (тестом, ревью, запросом в БД).
- Типичные аспекты: идентичность, источник правды, ответ API, транзакция, блокировки, идемпотентность, ретеншн, доступ, безопасность/ПДн, наблюдаемость, порядок обработки.
- Не дублируй весь раздел «Решение» — только то, что должно пережить будущие изменения.

### Последствия

Маркированный список, честно и с обеих сторон:

- что улучшится и для кого (кандидат, HR, разработчик, эксплуатация);
- принятая цена и риски — с жирными метками категорий: `**ПДн:**`, `**Спам:**`, `**Производительность:**`, `**Rollout:**`; рядом — чем риск смягчён;
- изменение поведения для существующих пользователей и данных;
- дополнительная нагрузка (лишние запросы, вставки, задачи);
- что становится обязательным для нового кода («новые POST должны либо…»);
- что откатить нельзя и почему;
- что сознательно не решено и вынесено отдельно.

### Рассмотренные и отклонённые альтернативы

Таблица `| Вариант | Почему отвергнут |`. Включай очевидные альтернативы, которые читатель предложит первым («отключить все ретраи», «серверная идемпотентность»), и конкретную причину отказа. Если в репозитории альтернативы принято давать внутри «Решения», можно так; главное — чтобы отвергнутые варианты были зафиксированы.

### Развёртывание

Добавляй, если выкатка не тривиальна: нужна остановка писателей, строгий порядок миграция → сервисы, предварительные SQL-проверки, окно обслуживания, smoke-проверки, невозможность отката. Перечисляй конкретные deployment'ы, воркеры, CronJob'ы и запросы. Если достаточно одной фразы о порядке («сначала миграция `0052`, затем API»), помести её в «Последствия».

### Реализация

Список ключевых файлов и модулей с тем, что в них изменено. Пути — от корня репозитория. Раздел помогает найти код решения через год; не превращай его в полный diff.

### Ссылки

- Связанные ADR — ссылкой и одной строкой о характере связи: «[ADR 0036](0036-…md) — политика форка; частично заменена этим ADR».
- Ключевые файлы, если нет раздела «Реализация».
- План (`.plans/<slug>.md`), инцидент, внешняя документация вендора.

## Связи между ADR

| Связь | Когда | Что сделать |
|---|---|---|
| **Заменяет** | Новое решение полностью отменяет старое | В шапке нового — `**Заменяет:**`; у старого статус → `Заменено [ADR NNNN](…)` + строка-указатель |
| **Частично заменяет** | Отменяется часть старого решения | В шапке нового — `**Частично заменяет:**` с аспектом; у старого статус → `Частично заменено [ADR NNNN](…)` |
| **Уточняет** | Старое решение остаётся в силе, новое его развивает или ограничивает | Только `**Уточняет:**` в шапке нового и ссылка в «Ссылках»; статус старого не меняется |

Связь всегда отражается в индексе (см. «Индекс»).

## Иммутабельность

Принятый ADR — исторический документ. После статуса `Принято` в нём можно менять **только**:

1. **Строку статуса** при замене: `**Статус:** Заменено [ADR 0045](0045-slug.md)` или `Частично заменено …`.
2. **Строку-указатель** сразу под шапкой: «Заменено: [ADR 0045](…) в части модели и метрик. Ниже зафиксировано решение на момент принятия».
3. **Раздел `## Коррекция YYYY-MM-DD: …`**, дописанный в конец (см. ниже).

Запрещено: переписывать контекст, решение или инварианты задним числом, удалять разделы, «актуализировать» имена под текущий код, исправлять ADR под новое решение. Устаревшие ссылки и расхождения с кодом фиксируются в индексе или отдельном отчёте сверки, а не правкой ADR.

Пока ADR в статусе `Предложено` (до реализации), его можно свободно редактировать; при мерже реализации статус меняется на `Принято`.

## Коррекции

Коррекция — дописанный в конец принятого ADR раздел `## Коррекция YYYY-MM-DD: <что исправлено>`. Используй её, когда **решение то же**, но вскоре после выкатки выяснилось, что факт или деталь реализации в ADR неверны: вендор не поддерживает параметр, URL в письме оказался внутренним, элемент админки бесполезен.

В коррекции: что оказалось неверным (с доказательствами — ошибка, инцидент, замеры), что изменено, какие инварианты остались прежними, нужна ли миграция. Добавь пометку `**Коррекция YYYY-MM-DD:** …` в конец строки ADR в индексе.

Пиши **новый ADR**, а не коррекцию, если меняется само решение, инвариант, модель данных или публичный контракт, либо прошло много времени и решение пересматривается по новым причинам.

## Индекс `docs/adr/README.md`

После создания ADR:

1. Добавь строку в основную таблицу: `| N | [NNNN-slug.md](NNNN-slug.md) | Суть |`. «Суть» — плотный абзац: что решено, ключевые идентификаторы, повод, главные отвергнутые варианты, связи («уточняет ADR 0038/0043»). Читатель должен понять решение, не открывая файл.
2. Если новый ADR заменяет или частично заменяет старый — отметь это в строке старого ADR (например, `**Заменён ADR 0031**` или `**Частично заменено ADR 0066** (аспект)`) и добавь или обнови строку в таблице связей (`Последующие замены и уточнения` или аналог).
3. Если в шапке индекса указаны счётчик ADR или дата сверки — обнови их.
4. Если индекса нет — создай его по `templates/readme-index.md` и внеси в него все существующие ADR.

## Стиль

- Язык — как в существующих ADR репозитория; идентификаторы кода не переводятся и пишутся в обратных кавычках.
- Факты вместо намерений: описывай фактическое поведение реализации. «Должно», «планируется» — только в статусе `Предложено` или в явно отмеченных отложенных задачах.
- Числа с единицами, даты в ISO, точные значения констант.
- Таблицы — для перечислений, вариантов и инвариантов; списки — для последствий; проза — для объяснения причин.
- Пиши «почему», а не только «что»: ценность ADR в обоснованиях и отвергнутых вариантах.
- Явно отмечай, что осознанно не делали и почему.
- Одно решение — один ADR. Если в изменении два независимых решения, напиши два ADR.
- Объём соразмерен решению: небольшое уточнение — полстраницы, смена модели маршрута — несколько страниц с runbook'ом.

## Чек-лист перед завершением

После bootstrap:

- [ ] Существующая инфраструктура ADR не найдена или переиспользована, параллельная структура не создана.
- [ ] Созданы `docs/adr/0001-record-architecture-decisions.md` и `docs/adr/README.md` на языке проекта.
- [ ] Правило ADR добавлено в один основной файл инструкций агентов.
- [ ] Ссылка на индекс ADR добавлена в существующую карту документации, если она есть.

Для каждого нового ADR:

- [ ] Файл `docs/adr/NNNN-slug.md`: номер следующий по порядку и свободен, slug в kebab-case описывает решение.
- [ ] Заголовок формулирует решение; шапка содержит статус, дату и все связи ссылками.
- [ ] Контекст содержит факты и потребность, но не решение.
- [ ] Решение конкретно: все имена, миграции, env, лимиты проверены `grep`-ом по коду.
- [ ] Инварианты — проверяемые правила в таблице.
- [ ] Последствия включают цену, риски, rollout и невозможность отката, если она есть.
- [ ] Отвергнутые альтернативы зафиксированы.
- [ ] Пустых необязательных разделов нет.
- [ ] У заменённых ADR обновлены только статус и строка-указатель; тела принятых ADR не изменены.
- [ ] Индекс обновлён: новая строка, отметки у заменённых, таблица связей, счётчик и дата.
- [ ] Относительные ссылки на ADR и документы открываются.
- [ ] Смежные документы в `docs/` обновлены, если решение меняет описанное в них поведение.
